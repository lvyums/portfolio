能力信号 #1 · 架构决策力

为什么我选择三阶递进而非纯 AI 方案

🧠 我的决策

项目启动时，摆在面前的有两条路：一是直接调 LLM API 搞定一切——实现最快，但每条日志都走大模型，成本高、响应慢、还可能在安全场景里产生幻觉。二是纯规则引擎——稳定可靠，但面对复杂攻击链和模糊日志时力不从心。

我选了第三条路：从"确定"到"智能"逐层递进。每一层解决自己最擅长的问题，解决不了的自然下沉。这不是技术炫技，而是成本账——让 70% 的请求在 5 毫秒内完成，剩下的 30% 才走更重的链路。

⚡

第一层：正则规则引擎

毫秒级 · 确定 · 零外部依赖

我基于 19 条 JSON 规则构建了快速匹配层。纯本地正则运算，零 API 调用。日志格式识别、关键词预筛、攻击类型自动分类——这些是确定性问题，正则足够。这层能处理约 70% 的常规场景，耗时不超过 5 毫秒。

⏱ 5ms 以内 🔍 19 条规则 💰 零成本 ≡ 零依赖
📚

第二层：RAG 知识库增强

精准检索 · 领域知识 · 可溯源

当正则覆盖不了时——比如合规审计需要比对等保 2.0 原文、采集需要推荐最佳实践——我构建了 ChromaDB 向量知识库。5 大分片、259 条领域知识，Embedding 三级降级保障可用性。RAG 层确保了所有回答有据可查，不会编造不存在的事实。

📖 5 大知识库 📄 259 条知识 🔗 三级降级 ✅ 可溯源
🧠

第三层：大模型智能推理

语义理解 · 灰色地带 · 场景化输出

前两层筛选后，只有真正需要语义理解的场景才触发 LLM——攻击链时序推理、跨阶段隐蔽模式识别、非标准日志智能解读。我选了 DeepSeek V4 Flash，设 10 秒超时自动降级、低温度 0.1 保证严谨。每一层都在为上层减负，LLM 只做它最擅长的事。

🧠 DeepSeek V4 ⏱ 10s 超时降级 🎯 仅复杂场景 📉 温度 0.1
💡 这个决策说明我

有成本意识——不盲目跟风 AI，知道什么时候该用、什么时候不该用。
能权衡取舍——在"快 vs 准"、"简单 vs 智能"之间找到了平衡点。
有系统思维——不是堆砌功能，而是设计了有层次的架构让各部分各司其职。

🤔

为什么第一层不用 LLM？

  • 日志格式识别是确定性问题——正则足够好
  • JSON 规则可维护、可调试、可热加载
  • 避免"每条日志都走 LLM"的高成本
  • 测试结果 100% 可预期，无不确定性
🎯

为什么第二层需要 RAG？

  • 安全领域知识专业封闭，LLM 训练数据不足
  • 等保 2.0 等标准需要原文引用，不能编造
  • 向量检索比 LLM 参数更精准可靠
  • 知识可独立更新，不影响业务代码
🧠

为什么第三层才用 LLM？

  • 攻击链时序推理需要语义理解能力
  • 非标准日志格式需要"类人判断"
  • AI 对话需要自然语言交互
  • 前两层过滤了 90% 无关调用
能力信号 #2 · 代码质量意识

我如何用设计模式治理项目复杂度

设计模式不是为用而用的炫技——它们是"当代码开始变乱时，自然出现的解法"。在项目迭代中，每当我发现"改一个地方要牵连五个文件"或者"这个逻辑散落在各处"，我就会停下来引入一个模式来治理它。

🏭

工厂模式 Factory Pattern

背景：一开始只有 SSH 和 Web 两种日志解析，后来陆续加了 WAF、防火墙、数据库、流量……如果每次新增都改路由层，代码会变成一团乱麻。

解法：LogParserFactory 统一管理所有解析器。新增一种只需继承 BaseParser + 一行 register()，上层零改动。

📌 信号：我有前瞻性设计意识，会为系统的可扩展性做规划
🔄

策略模式 Strategy Pattern

背景：6 种日志的解析逻辑完全不同（SSH 看登录尝试、Web 看 URL 参数、WAF 看攻击 payload……），但对外接口应该统一。

解法：每种日志一个策略类，全部实现 can_parse() + parse_fields()。攻击链检测也用了同一思路——关键词策略（快路径）→ LLM 策略（慢路径）。

📌 信号：我遵循开闭原则——对扩展开放，对修改封闭
📐

模板方法 Template Method

背景：每个解析器都要做"解析→校验→标记缺失字段"三步，代码重复了 6 次。

解法：BaseParser 定义解析模板，子类只需实现 can_parse 和 parse_fields，校验统一由父类 validate() 完成，消除 60% 重复代码。

📌 信号：我有消除重复的强迫症，知道公共逻辑应该收拢到一处
📦

上下文模式 Context Pattern

背景：6 个模块需要共享请求状态——采集阶段的结果要传给解析阶段，解析结果要喂给 LLM 分析。如果模块间直接传参，耦合度会非常高。

解法：ContextManager 按 request_id 隔离上下文。TTL 自动过期，上限 500 条防内存泄漏。

📌 信号：我考虑多用户并发和资源安全，不是写完功能就了事
⚡

两级管道 Two-Stage Pipeline

背景：日志量大的时候，每条都调 LLM 检测攻击链——成本爆炸、响应太慢。

解法：AttackChainMatcher 快慢双通道。Stage 1 纯正则在毫秒级完成关键词预筛，只有置信度不足时才降级到 Stage 2 LLM 语义增强。

📌 信号：我有性能优化意识，不做无谓的 API 调用
🔒

单例模式 Singleton Pattern

背景：日志管理器、正则关键词缓存——这些资源在整个进程周期内只需要一份实例。

解法：LogManager 全局单例 + 关键词惰性缓存。首次匹配即编译缓存，后续查询零开销。

📌 信号：我有资源管理意识，知道什么东西该共享、什么东西该隔离
💡 这些模式综合说明我

交给我的代码，不会是"能跑就行"的水平。我会考虑可维护性（别人接手看得懂吗？）、可扩展性（半年后加个功能要改几个文件？）、性能（这个调用真的有必要吗？）。这不是书本知识——是我在迭代过程中真正痛过之后，自然生长出来的习惯。

能力信号 #3 · 产品思维

为什么我坚持同时做Web 和 CLI

大部分安全工具只提供一个交互界面。但我观察到一个事实：Web 和 CLI 服务的不是同一群人，甚至不是同一个场景下的同一个人。安全运维工程师白天用仪表盘看报表，凌晨被叫起来应急响应时却只信任终端——因为终端更快、更直接、可以写脚本批量处理。

所以我决定：两个都做，共享同一套核心引擎。这不是工作量翻倍——web 端和 CLI 端调的是同样的 parse/correlate/audit 接口，只是交互方式不同。

🌐

Web 可视化平台

FastAPI + Vue 3 SPA · 22 个页面
  • 报表展示——攻击链可视化、合规差距雷达图、溯源报告在线预览
  • 团队协作——成员共享平台，无需各自配置环境
  • 低门槛——HR、合规审计角色也能操作，零命令行基础
  • 攻防实训——12 个内置场景，在浏览器中完成安全演练
  • 交互体验——下拉选择、表单填写、图表联动，即时反馈

适用于：日常巡检、报告审阅、团队协作、安全培训

⚡

CLI 命令行工具

log_trace_guard_cli · 纯终端交互
  • CI/CD 集成——在 Jenkins/GitLab CI 中作为 pipeline 步骤直接调用
  • SSH 远程——服务器无图形界面，直接 ssh 上去运行分析
  • 批量自动化——脚本化处理海量日志，cron 定时合规巡检
  • 管道输出——JSON 结构化输出，可被下游系统直接消费
  • 低资源——纯终端操作，512MB 内存的轻量服务器也能跑

适用于：应急响应、自动化流水线、远程调试、批量处理
