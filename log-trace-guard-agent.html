在研究院实习期间，我独立设计了这套安全日志溯源分析平台，核心思路是："用最合适的手段做最合适的事"。 不盲目依赖大模型，而是构建了 正则规则引擎 → RAG 知识库 → LLM 大模型 三阶递进架构， 让每一层各司其职。同时提供 Web 可视化平台 + CLI 命令行 双形态，覆盖从"日常巡检"到"自动化运维"的全场景。

架构核心

三阶递进推理架构

这是整个系统最核心的设计决策：不做"一刀切"的 AI 方案。安全日志分析存在大量可穷举、可量化的场景，全走 LLM 不仅成本高昂、响应慢，还会引入不必要的幻觉风险。我设计了从确定性到智能性逐层递进的三级架构——每一层解决自己能解决的问题，解决不了的自然下沉到下一层。

⚡

第一层：正则规则引擎

毫秒级 · 确定 · 零调用

基于 19 条 JSON 规则的快速匹配层，纯本地正则运算，零外部 API 调用。负责所有可穷举的日志解析、攻击关键词预筛、类型自动识别。这一层能处理约 70% 的常规场景，耗时不超过 5 毫秒。

⏱ 5ms 以内 🔍 19 条规则 💰 零成本 📦 零依赖
📚

第二层：RAG 知识库增强

精准检索 · 领域知识 · 防幻觉

当正则规则无法覆盖——比如合规审计需要比对等保 2.0 标准、采集架构需要推荐最佳实践——启动 ChromaDB 向量检索。5 大知识库分片（日志基础 / 合规审计 / 采集架构 / 技术脚本 / 实训案例），259 条领域知识，Embedding 三级降级策略保障可用性。RAG 层确保了回答有据可查，不捏造事实。

📖 5 大知识库 📄 259 条知识 🔗 三级降级 ✅ 可溯源
🧠

第三层：大模型智能推理

语义理解 · 灰色地带 · 场景化输出

经过前两层筛选后，只有真正需要语义理解的复杂场景才触发 LLM 调用：攻击链的时序推理、跨阶段的隐蔽攻击模式识别、非标准日志格式的智能解读。集成 DeepSeek V4 Flash，10 秒超时自动降级，T=0.1 低温度保证输出严谨。每一层都在为上层减负——LLM 只处理最复杂的"灰色地带"。

🧠 DeepSeek V4 ⏱ 10s 超时降级 🎯 仅处理灰色地带 📉 低温度 0.1

数据流转链路：逐层筛选，逐级增强

1 用户输入 / 日志上传 任何入口进入
→
2 正则规则引擎匹配 70% 场景在此终结
→
3 规则不足？RAG 检索 知识库增强
→
4 仍需语义推理？LLM 介入 仅复杂场景
→
5 结构化结果输出 统一格式
🤔

为什么第一层不用 LLM？

  • 日志格式识别是确定性问题——正则足够
  • JSON 规则可维护、可调试、可热加载
  • 避免"每条日志都走 LLM"的天价成本
  • 测试结果 100% 可预期，无不确定性
🎯

为什么第二层需要 RAG？

  • 安全领域知识专业且封闭——LLM 训练数据不足
  • 等保 2.0、ISO 27001 等标准需要原文引用
  • Embedding + 向量检索比 LLM 参数更精准
  • 知识可独立更新，不影响业务代码
🧠

为什么第三层才用 LLM？

  • 攻击链时序推理、隐蔽模式识别需要语义理解
  • 非标准日志格式的"类人判断"能力
  • AI 对话需要自然语言交互
  • 前两层已经过滤了 90% 无关调用
  • 低温度 + 超时降级保证可靠性

"这个架构的核心思想是：能确定的事就不猜，能查到的事就不编，猜和编的事才交给 AI。在安全领域，确定性与可溯源性比炫酷更重要。"

代码质量

多种设计模式驱动开发

设计模式不是为用而用的炫技，而是每当你发现"某个地方的改动要牵连 5 个文件"时，自然生长出来的解法。在迭代过程中，我逐步引入了 6 种设计模式来解耦、复用和治理项目复杂度。

🏭

工厂模式 Factory Pattern

新增一种日志解析器，只需继承 BaseParser + 一行 register() 注册，上层路由零改动。LogParserFactory 根据日志特征自动分配合适的解析器。

# 注册：一行搞定
LogParserFactory.register("ssh", SSHParser)

# 使用：自动分发
parser = LogParserFactory.get_parser(log_line)
🔄

策略模式 Strategy Pattern

6 种日志解析器（SSH/Web/WAF/Firewall/DB/Traffic）统一实现 BaseParser 接口，每个策略独立维护。攻击链检测也采用两级策略：关键词策略（快路径）→ LLM 策略（慢路径降级）。

class SSHParser(BaseParser):
  def can_parse(self, line) -> bool
  def parse_fields(self, line) -> ParsedLogFields

# 运行时自动选策略
parser = factory.get_parser(log_line)
📐

模板方法模式 Template Method

BaseParser 定义了解析的标准流程模板：can_parse(抽象) → parse_fields(抽象) → validate(通用)。子类只需实现两个抽象方法，校验逻辑由父类统一完成，减少了 60% 的重复代码。

class BaseParser(ABC):
  def validate(self, parsed): # 公共模板
    parsed.mark_missing()
    return parsed
📦

上下文模式 Context Pattern

请求全链路的状态管理器。ContextManager 按 request_id 隔离上下文，TTL 自动过期清理（上限 500 条防内存泄漏）。6 个模块共享同一个 context，下游感知上游状态，任意模块入口均可启动工作流。

ctx = ContextManager.create(user_input)
ctx.set_module_result("log_parse", result)
status = ctx.get_upstream_status("log_parse")
⚡

两级管道模式 Two-Stage Pipeline

AttackChainMatcher 采用"快慢双通道"：先纯本地正则在毫秒级完成关键词预筛（Stage 1），只有匹配置信度低于阈值或需要语义理解时才降级到 LLM（Stage 2）。大多数攻击链在第一阶段就搞定了。

# Stage 1: 毫秒级本地匹配
chains = matcher.match_keywords(lines)
# Stage 2: 按需 LLM 增强
if chains.confidence < 0.6:
  chains = llm.enhance(chains)
🔒

单例模式 Singleton Pattern

LogManager 全局日志管理器确保整个进程内只维护一个日志实例，消除重复初始化。类似地，正则关键词缓存（_keyword_cache）也采用惰性单例——首次匹配即编译并缓存，后续查询零开销。

logger = LogManager.get_logger()

# 关键词缓存单例
_keyword_cache: Dict[str, Pattern] = {}
pattern = _keyword_cache.get(keyword)
双形态设计

为什么同时做网页和 CLI

很多安全工具只提供一个交互界面。但我发现：Web 和 CLI 服务的不是同一群人，甚至不是同一个场景下的同一个人。安全运维工程师在工位上用着 Web 仪表盘，凌晨应急响应时却只相信终端。因此我决定同时交付两个版本，共享同一套核心引擎。

🌐

Web 可视化平台

FastAPI + Vue 3 SPA
  • 报表展示—攻击链可视化、合规差距雷达图、溯源报告在线预览
  • 多人协作—团队成员共享同一个平台，无需各自配置环境
  • 非技术人员友好—HR、合规审计等角色也能操作，零 CLI 门槛
  • 实训攻防—12 个内置攻防场景，在浏览器中完成安全演练
  • 交互式操作—下拉选择、表单填写、图标联动，即时反馈
22 个页面 6 大导航模块 SPA 架构 RESTful API
⚡

CLI 命令行工具

log_trace_guard_cli · 终端交互
  • CI/CD 集成—在 Jenkins / GitLab CI 中作为 pipeline 步骤直接调用
  • 远程 SSH 服务器—无需图形界面，在公司服务器上直接运行分析
  • 批量自动化—脚本化处理海量日志，cron 定时执行合规巡检
  • 管道式输出—JSON 结构化输出可直接被下游系统消费
  • 低资源消耗—纯终端操作，512MB 内存的轻量服务器也能流畅运行
零图形依赖 管道兼容 低内存 脚本化
