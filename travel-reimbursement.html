N+1 查询优化

使用 CompletableFuture 并行查询 4 张关联表，将串行查询改为并行执行，列表查询性能提升 3 倍。

// 并行查询4个关联表 CompletableFuture<Map<String, ReimEmployee>> empFuture = CompletableFuture.supplyAsync(() -> { return employeeService.list(wrapper).stream() .collect(Collectors.toMap(...)); }, reimQueryExecutor); CompletableFuture.allOf(empFuture, deptFuture, compFuture, btFuture).join();
2

幂等性保障

基于 ConcurrentHashMap 实现轻量级幂等校验拦截器，3 秒自动过期，防止重复提交。

public class IdempotentSubmitInterceptor { private static final ConcurrentHashMap<String, Long> REQUEST_MAP = new ConcurrentHashMap<>(); @Override public boolean preHandle(...) { String key = "form_submit:" + formUid + ":" + action; if (!IdempotentUtil.tryAcquire(key)) { return false; } return true; } }

乐观锁并发控制

使用 MyBatis-Plus @Version 注解实现乐观锁，配合状态校验和全局异常处理，三层防护确保并发安全。

@Version private Integer version; // 全局异常处理器捕获乐观锁冲突 @ExceptionHandler(OptimisticLockException.class) public Result<String> handle(...) { return Result.error(409, "数据已被其他人修改，请刷新后重试", null); }

Challenges

技术挑战与解决方案

深入业务场景，针对性解决核心技术难题

1

N+1 查询性能瓶颈

▼
问题

报销单列表查询时，每条记录需关联查询员工、部门、公司、业务类型 4 张表，10 条记录产生 40+ 次 SQL 查询。

解决方案

使用 CompletableFuture 并行查询，先收集所有关联 ID，批量查询后构建 Map 缓存，从缓存中获取关联数据。查询时间从 O(N×4) 降为 O(1)。

// 收集所有不重复的关联ID Set<String> reimburserIds = forms.stream() .map(ReimForm::getReimburserId) .filter(Objects::nonNull) .collect(Collectors.toSet()); // CompletableFuture并行查询4个关联表 CompletableFuture.allOf(empFuture, deptFuture, compFuture, btFuture).join();
2

重复提交导致数据异常

▼
问题

用户快速双击提交按钮，前端未做防抖处理，导致后端收到两次请求，产生重复数据。

解决方案

实现基于 ConcurrentHashMap 的幂等校验拦截器。通过 formUid + 操作路径生成唯一 key，3 秒内重复请求直接拒绝。定时任务每 10 秒清理过期 key。

public static boolean tryAcquire(String key) { Long previous = REQUEST_MAP.putIfAbsent( key, System.currentTimeMillis() + 3000); return previous == null; }
3

并发更新数据覆盖

▼
问题

多人同时编辑同一报销单，后提交的覆盖先提交的修改，导致数据丢失。

解决方案

采用三层防护：①乐观锁 version 字段控制更新冲突；②操作前校验单据状态是否允许；③全局异常处理器捕获乐观锁异常，返回友好提示。

@Version private Integer version; // updateById 时自动带 WHERE version = ? // 版本不匹配则更新失败，触发乐观锁异常
4

补助金额级联计算

▼
问题

修改某一天的补助明细后，需要同步更新补助总额和报销单总额，涉及多表联动。

解决方案

设计级联重算机制：日历明细修改 → 重算当前补助总额 → 重算报销单总额。使用 @Transactional 保证数据一致性。

// 级联重算流程 日历明细修改 → recalculateSubsidyTotal(subsidyUid) → recalculateFormTotals(formUid) // 汇总所有未删除的日历明细 for (ReimSubsidyCalendar cal : calendars) { if (cal.getMealSelected() == 1) mealTotal += cal.getMealActualAmount(); }
5

浮点数精度丢失

▼
问题

使用 double/float 存储金额，累加计算时出现精度丢失（如 0.1 + 0.2 ≠ 0.3）。

解决方案

所有金额字段统一使用"分"为单位，以 INT 类型存储。前端展示时再除以 100 转换为元。彻底避免浮点数精度问题。

// 数据库存储：10000（分） // 前端展示：10000 / 100 = ¥100.00 // 补助标准配置（单位：分） private static final int[] FIRST = {10000, 4000, 4000}; // 一线城市：餐补¥100/天 交通¥40/天 通讯¥40/天
